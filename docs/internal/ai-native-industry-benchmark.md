# AI Native 行业架构对标与落地次序

> 核查日期：2026-09-27。本文对照 Snowflake、Apache Spark、Apache Gluten 的官方一手资料及本工作区源码。它是当前实现的差距记录，不替代[目标架构](ai-native-target-architecture-and-implementation-plan.md)、[Snowflake/Gluten 设计评审](ai-native-snowflake-gluten-distributed-architecture-review.md)或持续更新的[实施账本](ai-native-roadmap.md)。源码正在并行修改；下述“已证明”只限引用的测试范围。本文未运行构建或 E2E。

## 结论

Pangrova 选定的边界与主流架构方向一致：Coordinator JVM **仅负责控制面**的规划、授权、绑定、准入、调度、fencing 与提交元数据；分布式 merge、group、Top-K、检索和行级计算留在 Native Worker。StageDAG 将交换边界切成任务，Worker 间使用 Native Flight；所有阶段使用**同一个 canonical v2 proto**，不引入 vector 专用任务协议。索引构建采用持久 page 和不可变 generation。当前最大差距已从“是否有这些抽象”转向三个可以验收的闭环：**跨 Worker 故障时 shuffle 与 task 的恢复；跨 Coordinator 的资源接纳与隔离；作为持久、可运维对象的 Search Service 与增量索引生命周期**。完整 Step 0–8 发布门禁和多 Worker 故障矩阵仍未在最终源码上通过，不能由单项组件测试推导生产规模能力。[Pangrova 当前证据](ai-native-roadmap.md#08-2026-09-27-分布式执行与物理出站预算复证进行中)

## 落地优先序与权衡

1. **P0：先补完整性和资源安全的分布式故障矩阵。** 使用最终同源码构建，测试双 Worker、多 stage JOIN/聚合/Top-K；在 producer 完成前后杀 Worker、断 Flight、延迟/重复 task report、取消和慢消费者。要求 `COMPLETE` 只有全分片有效输出，旧 attempt 不可提交，重试没有重复行；同时记录每条流的峰值在途字节与 Native 实际内存。若当前 direct shuffle 只能从 source snapshot 重算，就把这作为显式恢复策略与成本边界，不能宣称持久 shuffle。此项优先于 AQE 和弹性缩容，因为后二者会扩大恢复路径。
2. **P1：把准入做成可测的多 Coordinator 资源控制。** 区分 task 内存上限、节点实际占用、shuffle 保留额度、CPU/transport 并发；为每个 Worker 维护带 heartbeat generation 的 in-flight shadow placement，Worker 拒绝仍是权威。以多 Coordinator 同时派发、过期心跳、ACK 丢失、取消、缩容做竞争测试，并给出吞吐/排队 P99。独立 serving 与后台 refresh pool 可以先是逻辑隔离，物理隔离应由干扰实验决定；额外 pool 会牺牲低负载利用率。
3. **P2：交付最小 Search Service 闭环。** 只先支持一条 source query、稳定 PK、一个 text 与一个 vector source、明确排序版本。实现 `CREATE/ALTER/DESCRIBE`、目标新鲜度、独立 indexing/serving 状态、增量 refresh、generation CAS、旧代 serving 与状态/成本接口；用真实 public SQL→Native→服务查询 E2E 验证。把 rerank 可关、延迟和质量差异做可观测配置；不要在最小对象阶段追求所有算法组合。
4. **P3：在安全基线上做拓扑自适应与弹性。** 引入 runtime partition bytes/rows/skew 后，仅对未启动 stage coalesce/split、改变 reducer fan-in；以 pinned snapshot、generation、policy/model 与 schema 保持语义。远端 shuffle 或可证明的重算是 Worker 缩容的先决条件。AQE 增加调度复杂度和缓存波动，须以尾延迟及单位成本证明收益。

## 证据使用边界

- Snowflake 官方文档披露的是产品语义与部分公开架构，不披露 Cortex Search 的内部分片格式；Pangrova 的 manifest、Native 算子和刷新协议是本项目设计选择，不能写成 Snowflake 实现细节。
- Gluten 的 automatic fallback 是 Spark 兼容机制；Pangrova 的 canonical Native 查询要求调度前 capability 准入。两者目标不同，不能以 Gluten 的 fallback 为 Pangrova 静默降级背书。[Gluten](https://gluten.apache.org/)
- 单项测试、源码存在、ADR 目标均不等于生产验收。最终发布判断仍以[持续实施账本](ai-native-roadmap.md)、同源码 Step 0–8、完整多 Worker 故障与负载证据为准。
