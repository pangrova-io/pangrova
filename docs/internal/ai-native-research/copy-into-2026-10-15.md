# COPY INTO execution boundary, 2026-10-15

## 2026-10-21 typed, admitted source preparation

`/v1/task/copy-stage` now carries `SourcePreparationRequest` in the sole v2
schema, with its exact task/owner identity, source-command digest, deadline and
resource grant. It has no relational plan, write task kind or Native executor.
The private mTLS envelope retains the bearer separately from canonical bytes.
`SourcePreparationResult` carries either the validated managed proof or a bounded
error, cumulative usage, the exact request checksum and actual I/O join state.

Preparation shares TaskManager's canonical admission/seal registry. A seal that
arrives first prevents subsequent source I/O. An active source owner retains
its node JVM reservation and tenant concurrency/memory reservation until real
I/O exits and its SDK client and draft are released. Failed cleanup retains the
exact owner for another cleanup attempt. Fatal producer errors are rethrown,
while their real cleanup outcome and entered usage remain available. Typed
preparation success never becomes an invented successful Native TaskReport;
the generic seal is exit-only evidence, and the separate preparation receipt
holds its outcome. Compact terminal retention contains usage/outcome, without
retaining the private source URI or bearer. A replay reauthorizes against the
Coordinator's durable proof and performs no object payload I/O.

Before source payload I/O, known size S must fit source GET plus managed readback
(2*S read), publication (S write), draft (S spill), and the admitted stream buffer.
Each request/chunk consumes the same allowance. Entered requests are never
refunded; the same failed attempt cannot restart payload I/O with its old grant.
Admitted GET and PUT requests disable SDK payload retries. PUT preserves its
conditional publication header. The real SDK HTTP test checks one admitted PUT
versus three ordinary attempts and checks every conditional header. This follows
[AWS request-specific plugins](https://docs.aws.amazon.com/java/api/latest/software/amazon/awssdk/core/RequestOverrideConfiguration.Builder.html)
and is verified against the actual locked SDK 2.25.16 classpath. Failed streaming
reads continue to abort before close; ordinary Apache `close()` can otherwise
read the remaining body, as documented by
[AWS ResponseInputStream](https://docs.aws.amazon.com/java/api/latest/software/amazon/awssdk/core/ResponseInputStream.html).

The actual PostgreSQL/MinIO/mTLS/JNI/Flight test uses one Native runtime and a
production TaskManager for preparation and relational execution. It checks exact
read/write/spill usage, source deletion followed by proof replay, released node
and tenant reservations, exact Native values, and revoked replay with retained
usage. The initial current-batch run passed 1/1 in 19.550 seconds; the final packaged
artifact passes 1/1 in 14.449 seconds. A capacity counterexample first failed:

source version selection from preparation of a later Native read: a missing

The next production wiring must preserve this order:

1. Resolve the authorized profile and target identity; stage and persist an exact

## Evidence and semantics

- The grammar accepts `COPY INTO target FROM 'uri'` with file options and
  `COPY INTO target FROM (setQuery)`, but the previous AST builder had no
  `visitCopyIntoStatement`. No URI discovery, file scanner, loaded-file
  identity, or COPY commit path was wired. Four existing E2E cases named a
  nonexistent `s3://test-bucket` location and only checked command success;
  they did not establish that any row was loaded.
- [Snowflake COPY INTO](https://docs.snowflake.com/en/sql-reference/sql/copy-into-table)
  applies its `FROM (SELECT ...)` transformation to staged files. It also
  specifies file format and filtering options for file loads. An arbitrary
  table-to-table query is therefore a Pangrova extension, not claimed
  Snowflake-compatible COPY syntax.
- [Databricks COPY INTO](https://docs.databricks.com/aws/en/ingestion/cloud-object-storage/copy-into/)
  promises retryable, file-level idempotent ingestion: files already loaded
  are skipped. Pangrova's table-to-table SELECT extension has INSERT SELECT
  semantics and appends rows on each execution; it cannot inherit that
  file-ingestion guarantee.
- [Iceberg's specification](https://iceberg.apache.org/spec/) makes an atomic
  metadata pointer swap the commit boundary. A safe future file loader must
  associate selected source-file identities with this commit boundary (or a
  fenced journal), and determine the result after ambiguous commit responses.
- [Databricks' COPY INTO contract](https://docs.databricks.com/gcp/en/sql/language-manual/delta-copy-into)
  skips files already loaded, including modified files at the same path. Its
  [external location model](https://docs.databricks.com/aws/en/data-governance/unity-catalog/securable-objects)
  binds a storage credential to a path and requires a separate file-read
  privilege. These are separate from target-table INSERT authorization.

## File-loader acceptance still open

The existing `StorageProfile` SPI now parses object URLs and matches the
configured backend, bucket, and complete prefix path segments. It rejects
ambiguous encodings, traversal, query/fragment decorations, and LOCAL URLs;
LOCAL requires canonical filesystem and symlink resolution before it can
authorize a file. This SPI is an authorization prerequisite, not an active
COPY source: `COPY INTO ... FROM 'uri'` still fails closed at parsing, and the
production profile registry is now persistent and has exact
`READ_STORAGE_PROFILE` grants. Credentials remain Worker-local; the SQL URI
path is still disconnected.

The original `WriteCommitEntry` and `WriteCommitFingerprint` deduplicated one
query's commit replay using its query ID and fragments. V58 adds an immutable
COPY claim binding to the one fingerprint contract for all journaled writes;
the durable file claim remains the cross-query identity. The URI SQL route is
not yet connected, so adding a scanner alone would still duplicate rows on a
second run. File identities must be frozen from
the authorized file listing, and their committed state must be published with
the target table's atomic commit or through a fenced, reconcilable journal.
Concurrent COPY writers must recheck identities after commit conflicts, while
ambiguous commit responses must reconcile against the target's committed
state before retrying. Pangrova chooses version-aware dedup for the exact-S3
slice: the same URI and S3 version can be loaded into one Iceberg table UUID
only once, while a later version at that URI is a distinct file load. This is
an explicit difference from Databricks' documented path-only behavior. The
durable admission claim exists; V58's snapshot-marker/publication reconciliation
is implemented separately; its focused PostgreSQL tests pass, while the
end-to-end URI path remains unvalidated.

### Smallest complete file path to build

The first complete vertical slice should be one exact `s3://bucket/key.parquet`
object into an Iceberg target. It should require a configured, durable S3
external location, an authenticated file-read grant, target INSERT permission,
and a versioned source object. Directory listing, `PATTERN`, CSV, JSON, OSS,
GCS, ADLS and LOCAL remain rejected in this slice. A single exact object
avoids pretending a directory listing is a stable snapshot. The S3 `versionId`
must be captured by HEAD and used to [read that exact version](https://docs.aws.amazon.com/AmazonS3/latest/userguide/RetrievingObjectVersions.html),
or copied by source version to immutable managed staging before the Native
reader opens it; a path or ETag alone cannot pin the bytes read during a
concurrent overwrite. Pangrova's Velox S3 reader has no verified versioned
read contract. A Worker-local stager now performs exact-version GET and a
byte-verified conditional publication into managed storage, with real MinIO
coverage; SQL dispatch and Native scanning still need the typed binding.

The execution route should keep the one SQL→Calcite→Substrait→JNI→Native
scan→Native write→catalog commit path. A typed URI COPY AST must bind a
query-owned, read-only file relation with Parquet footer schema checked
against the Iceberg target; its connector emits a canonical v2 `DataSplit`
with `FILE_FORMAT_PARQUET`, exact immutable staged object identity, and a
trusted object-store execution binding. `PlanSplitSourceExtractor` and
`SplitFetcher` then see an ordinary bound scan. `NativeReadSplitBinding`
must validate the new COPY connector's tenant and managed-object location;
it must never trust SQL-supplied credentials.
Native already has a Parquet DWIO reader, but does not yet have this file
connector or a COPY-specific read authority.

The target write must carry a source-file identity into the immutable write
intent and Iceberg snapshot marker. The durable admission claim is keyed by
tenant, real Iceberg table UUID, canonical source URI, and exact S3 version;
content SHA-256/size and profile incarnation/revision are immutable evidence,
not parts of the dedup key. A later version at the same path can be claimed
independently. The claim must be fenced before Native work; a successful
Iceberg commit must publish its digest alongside the write fingerprint in the
snapshot summary. A separate durable completion record can be written only
after the same marker is verified in the target's current snapshot ancestry.
On lost commit response or coordinator restart, an unproven claim remains
pending and blocks another execution; timeout never releases it. Keep the
marker reachable until reconciliation completes; expired history is ambiguous,
not evidence of an uncommitted write. The existing query-ID commit fingerprint
alone is insufficient for cross-query file deduplication. PostgreSQL's unique
claim key and `INSERT ... ON CONFLICT DO NOTHING` serialize competing claimants;
under [Read Committed isolation](https://www.postgresql.org/docs/16/transaction-iso.html),
a fresh read after the insert sees the committed winner and checks its complete
identity and immutable evidence.

### Commit-to-claim crash window and V58 implementation

Before V58, the distributed-write order in
[`NativeTaskWriteCompletion`](../../../pangrova-coordination/pangrova-coordination-core/src/main/java/org/pangrova/coordinator/query/task/NativeTaskWriteCompletion.java)
is: persist `WriteCommitEntry`, call `finishDistributedWrite`, mark the write
journal committed, then retire it through `WriteCommitJournal.purge`. The
[`JdbcWriteCommitJournal`](../../../pangrova-metadata/src/main/java/org/pangrova/metadata/coordination/JdbcWriteCommitJournal.java)
can delete an acknowledged committed entry.
[`V57__copy_file_claims.sql`](../../../pangrova-schema-migrations/src/main/resources/db/migration/V57__copy_file_claims.sql)
persists the source claim and execution ID, but does not yet persist the write
commit fingerprint or a completed outcome. Adding file-claim completion after
the existing journal retirement would leave a crash window: Iceberg could
contain the rows, the journal could be purged, and the claim would remain
pending without the fingerprint needed by the existing
[`IcebergDistributedCommitMarker.publishedSnapshot`](../../../pangrova-connector/pangrova-connector-iceberg/src/main/java/org/pangrova/connector/iceberg/IcebergDistributedCommitMarker.java)
lookup. URI COPY is still rejected before this route.

The complete route must durably bind claim key, claim digest, execution ID,
table UUID, and write commit fingerprint **before** the Iceberg attempt. Put
the claim digest in the same Iceberg snapshot summary as that fingerprint and
the loaded data. After `finishDistributedWrite`, verify that exact marker in
the current table UUID and snapshot ancestry, durably record the verified
claim completion, then permit journal retirement. Recovery repeats that
verification from the immutable claim/fingerprint binding; it neither creates
a new execution claim nor treats a missing marker after snapshot expiration as
proof of abort. [Iceberg's atomic metadata swap](https://iceberg.apache.org/spec/)
makes the snapshot the data-visibility boundary, whereas the PostgreSQL claim
completion is a separate transaction and therefore needs this reconciliation.
The ordinary INSERT no-fragment branch in
[`IcebergWriteCommitter`](../../../pangrova-connector/pangrova-connector-iceberg/src/main/java/org/pangrova/connector/iceberg/IcebergWriteCommitter.java)
is a no-op without a snapshot; the COPY-bound branch now rejects that outcome
unless the exact marker is already reachable. An empty Parquet source needs
a real marker-bearing commit or must remain unsupported; it cannot be
reported as a completed load without evidence.

V58 changes the journaled-write fingerprint once for every distributed write:
ordinary writes encode an explicitly absent COPY claim, while COPY writes
include the admitted claim key, generation, digest, and Iceberg table UUID.
The migration refuses startup with **any** old journal row, including a
COMMITTED row that can still anchor deferred work. PostgreSQL binds a COPY
intent to the immutable file claim, refuses COMMITTED without its durable
publication, and prevents deleting an unresolved COPY redo record. The
Iceberg writer stores the claim proof in the same snapshot summary as its
fingerprint. Coordinator completion records the connector-verified snapshot
ID before marking COMMITTED or purging the journal; recovery rechecks that
the recorded marker and snapshot are still in the current table ancestry.
If Iceberg published but the PostgreSQL publication failed, the PENDING
intent is retained and recovery repeats the exact marker check. A historical
PostgreSQL row by itself never establishes current table contents.

Focused real PostgreSQL migration and publication tests pass (6 tests, zero
skips), and a real HadoopCatalog marker/rollback class passes (15 tests, zero
skips). These are component-level evidence for the journal-retirement order,
not SQL/Worker/Native COPY evidence. External Iceberg rollback or snapshot expiry can remove
the marker after an earlier success; a later claim check must not infer
"already loaded" from the historical publication alone. Generation-based
reload is rejected until the target catalog provides an atomic expected-head
fence. These boundaries remain open for URI COPY acceptance.

Acceptance needs real MinIO with versioning and an actual Parquet object,
through SQL and JNI to Iceberg row values: first load, second-run zero new
rows, concurrent same-file COPY, source overwrite during staging, invalid
schema, denial outside external-location scope, worker failure before commit,
and ambiguous Iceberg commit with restart reconciliation. The existing
`S3FileDeployment` MinIO fixture offers real object-store plumbing,
but its current FILE callback configuration does not itself authorize COPY.

### V59 source-read admission boundary

V59 introduces a durable, single-attempt source-read admission. The Coordinator
must issue a private 256-bit bearer ticket only after checking the authenticated
tenant and current `READ_STORAGE_PROFILE` grant, exact profile incarnation and
revision, canonical S3 URL, deadline, and current execution anchor. Redemption
rechecks these facts under the PostgreSQL authority gate. A revoke followed by
regrant advances a transactional authorization revision, so it cannot revive
an older ticket. The staged proof records the exact S3 version and an immutable
managed-object URI with content SHA-256 and size; an identical retry reads and
verifies that managed object without fetching the original source again. These
facts are scoped to one durable staging attempt. The Coordinator redemption/record
HTTP resource and Worker staging command now pass a focused real PostgreSQL,
authenticated HTTP, and versioned MinIO test (4/4, zero skips). The V59
PostgreSQL authority/failover class passes 17/17, zero skips. These tests
cover staging and durable proof only; no SQL/Native task dispatch invokes the
command. URI SQL stays rejected.

V59 now checks the current PostgreSQL `coordinator_leader` lease epoch and
database-clock expiry under a row lock in the same transaction as issue,
redeem, and proof record. The execution anchor remains a separate query-owner
fence. A newly issued ticket under an obsolete control epoch is rejected even
before a canonical Worker `TaskRequest` exists; a real leader takeover fences
redemption and proof record for older tickets. This does not replace the later
Worker task-admission and final Iceberg publication fences.

The admission table cannot yet be garbage collected safely. V59 rejects
ordinary DELETE/TRUNCATE and has no terminal claim or journal reference that
would prove an expired ticket is irrelevant to ambiguous commit recovery.
Rows therefore accumulate without bound. A controlled archival/GC protocol,
with terminal publication proof and an auditable operator, is a production
blocker; deadline-based deletion alone would be unsafe.

The managed root URI is only a logical bucket/prefix name. The V59 draft now
binds a separate versioned digest of the SDK client's explicit S3 backend origin, region,
bucket/prefix, expected bucket owner, encryption policy and path-style mode into
the durable admission and the canonical staging command. A Worker with the same
`s3://` root on a different endpoint must reject the task before object I/O.
The production managed backend must configure an explicit HTTPS SDK endpoint
override; otherwise AWS SDK environment, JVM or shared-config endpoint overrides
could silently redirect a nominal region-default client. The client override
is compared with validated storage settings before an identity can be issued.
Consequently region-default AWS S3 configuration is not yet accepted for this
COPY path; an operator must explicitly configure the regional HTTPS origin.
The Worker materializer verifies the managed object's full SHA-256 and size
before exposing a task-private local Parquet file, and deletes it on close.
The real MinIO materializer class passes 7/7 and the current-source real
PostgreSQL/HTTP/MinIO class passes 4/4, zero skips, including the backend
identity and negative HTTP cases.

The private ticket travels in JSON bodies. A real DEBUG-level HTTP test found
that Jetty can render raw request buffers, including a ticket nonce, before
Jersey's exception mapper runs. The production Logback configuration therefore
pins `org.eclipse.jetty` at WARN and disables automatic config reload; the COPY
resource and Coordinator HTTP startup reject a logger configuration with Jetty
wire categories at DEBUG/TRACE. A Logback TurboFilter also denies subsequent
Jetty DEBUG/TRACE events if a logger level is changed while the server runs.
Replacing/resetting the entire Logback context remains inside the trusted
operator boundary and requires an explicit operational prohibition or a stronger
transport-level secret protocol. The current Coordinator-to-Worker
dispatcher originally constructed only plain `http://` URLs. V61 routes a
ticket-bearing COPY task through the dedicated mTLS listener when present and
rejects it before serialization when absent. The production
Worker-to-Coordinator redemption client requires HTTPS; an explicit test-only
factory permits local loopback HTTP in integration tests. Private endpoint
exception mapping suppresses request-derived parse messages and stack traces.

### V61 private task-control transport prerequisite

The Worker opens a second Jetty listener with required client certificates
only when a nonzero `worker.copy.task-tls-port`, transport TLS material, and
internal service authentication are configured. Ordinary Flight TLS alone does
not open this listener. Its fixed port is advertised at registration and retained in the JDBC worker
registry for Coordinator failover recovery. Only a COPY task with a private
source-read ticket uses that port. The Coordinator builds an HTTPS URL with
the registered host and its configured CA, client certificate, and key. It
rejects missing TLS material, an unadvertised secure port, or missing service
authentication before serializing the bearer ticket. Worker task admission
rejects a ticket received on its plain HTTP listener. Real TLS tests cover a
trusted client certificate, a missing client certificate, and cleartext against
the TLS listener; JDBC recovery tests cover the port.

The separate `/v1/task/copy-stage` operation now accepts a typed canonical
source preparation and private ticket through this listener, validates epoch,
deadline, owner and canonical digest before staging, and returns its exact
managed-object proof or failure together with cumulative usage and I/O join state. Jetty rejects plaintext on this path before JSON bearer parsing.
Production activation also requires managed S3 FILE storage, a Worker staging
root, and an HTTPS Coordinator URL; the current staging size cap is 1 GiB.
The Postgres/MinIO integration test drives this operation through real Worker
mTLS HTTP, checks the managed bytes against the source Parquet file, deletes the
original S3 version, and repeats the same attempt to prove no source re-pin.
Concurrent repeats of one attempt share the first result; a changed ticket or
canonical task conflicts. Expired in-memory attempt tombstones are retained for
ten minutes before capacity recovery. The non-deletable Coordinator admission
row has a unique `(tenant, execution, staging_attempt)` key and refuses expired
redemption, so it remains the authority after local tombstone eviction. Failed
staging retains its terminal usage and any unfinished cleanup owner; a repeat
cannot reuse its consumed allowance. Content-addressed managed objects require
lifecycle garbage collection if publication succeeds but proof recording fails.

COPY source and managed-object clients now use dedicated AWS SDK clients with
two-minute whole-call and 30-second attempt limits, five-second connection and
acquisition limits, and a 25-second Apache socket read limit. This does not
change the shared AI FILE client. A ten-minute monotonic wall limit also checks
each source and managed-object transfer, so a peer that continually trickles
bytes cannot retain a staging lease indefinitely. Failed or rejected GETs call
`ResponseInputStream.abort()` before resource close; ordinary Apache stream
close can otherwise drain the remaining response body. Controlled HTTP fault
tests cover a stalled partial body, a mismatched version with unread body, and
a trickling body; each exits within the bound, closes the S3 client, and leaves
no local `.part` file. The stage-only lease close waits for that bounded I/O
before closing its owned managed client. See [AWS SDK timeout guidance](https://docs.aws.amazon.com/sdk-for-java/latest/developer-guide/timeouts.html)
and [ResponseInputStream abort semantics](https://docs.aws.amazon.com/java/api/latest/software/amazon/awssdk/core/ResponseInputStream.html).

The Worker-to-Coordinator admission client also has a ten-second explicit
deadline around the *entire* HTTP response, including its 64 KiB bounded
body subscriber. JDK 17's `ofInputStream()` returns once headers arrive, and
the JDK request timeout alone did not stop a stalled body in a controlled
test. The client now waits on `sendAsync()` with a timed future and calls
`cancel(true)` on timeout or interruption. A loopback raw-socket test confirms
the caller returns inside the deadline and the server observes the cancelled
HTTP/1.1 connection close; a chunked oversized-body test confirms the size
limit. JDK cancellation is asynchronous and cannot guarantee an exact instant
of socket release on every transport. See [JDK 17 body subscriber semantics](https://docs.oracle.com/en/java/javase/17/docs/api/java.net.http/java/net/http/HttpResponse.BodySubscribers.html)
and [cancelable `sendAsync()` behavior](https://docs.oracle.com/en/java/javase/17/docs/api/java.net.http/java/net/http/HttpClient.html).

This transport prerequisite does not authorize URI SQL. `COPY INTO ... FROM
'uri'` still fails in the parser, and the Worker pre-Native staging gate remains
in place. Source version selection, Parquet scan binding, durable file claim,
and Iceberg snapshot publication must form one reconcilable end-to-end write
before opening URI ingestion. Exact S3 `versionId` is material to this design:
[S3 GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html)
returns the named version only when supplied. The
[Parquet format](https://parquet.apache.org/docs/file-format/) locates column
chunks through footer metadata, so a staged file must be validated by the
actual reader rather than by its filename. The
[Iceberg reliability model](https://iceberg.apache.org/docs/1.7.1/reliability/)
uses an atomic metadata-pointer commit and optimistic retries; file claims
cannot be declared committed before reconciliation with that snapshot.
The malformed-private-body nonce log-leak regression passes in the current
4/4 HTTP class. The dedicated Worker mTLS task listener is implemented and
tested. Production Worker-to-Coordinator HTTPS ingress and trust configuration
still require deployment validation; the local end-to-end test uses an explicit
loopback-only redemption transport. URI SQL remains closed until the typed
Parquet split and durable claim/commit binding are implemented and verified.

[Jetty's troubleshooting guide](https://jetty.org/docs/jetty/10/operations-guide/troubleshooting/index.html)
confirms that `org.eclipse.jetty` DEBUG recursively enables its HTTP parser,
I/O and server categories. [Logback's architecture guide](https://logback.qos.ch/manual/architecture.html)
defines effective child logger levels; its [configuration guide](https://logback.qos.ch/manual/configuration.html)
documents automatic reloading when `scan=true`.

The migration rejects ordinary direct SQL updates, deletes and truncation of
the authorization-revision row. A ticket also freezes the Coordinator-selected
managed storage root; a recorded proof must name the exact content-addressed
object below that root and the admitted tenant scope. The revision guard
protects against accidental or unauthorized DML through the runtime schema.
It does not defend against a
malicious PostgreSQL schema owner: the current bootstrap uses one metadata JDBC
principal for Flyway migrations and runtime access, and that principal can
alter or remove triggers. Production separation of migration and runtime DB
roles remains necessary before claiming resistance to a compromised DB owner.

Before exposing URI COPY as successful, implement an authorized storage
location/profile resolution, a bounded file-list snapshot and deterministic
file identity, format-specific native scanning, and a durable identity/commit
record tied to the Iceberg table commit. Test real local or object-store
files, retries including ambiguous commit results, concurrent COPY writers,
file mutation/replacement, malformed records, and target rollback/no partial
commit. A URI syntax test or a fake S3 address is not end-to-end evidence.
